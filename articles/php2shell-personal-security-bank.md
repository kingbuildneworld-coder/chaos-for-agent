# PHP大漏洞，个人怎么防

**2026 年 10 月 21 日，PHP 官方紧急发布 8.5.12、8.4.27、8.3.36、8.2.35 四个安全版本，修复被安全社区统称为“php2shell”的两个关键远程代码执行漏洞。**

**两个漏洞编号为 CVE-2026-109618 和 CVE-2026-109619，CVSS v4.0 评分均为 9.2（满分 10，属“严重”），允许攻击者在不登录的情况下，在服务器上远程执行代码。**

**真正可怕的是触发位置：在 Apache 搭配 mod_php 的部署里，恶意请求在任何应用代码运行之前就可能触发漏洞，这意味着传统的登录校验、网页应用防火墙都难以挡住。**

**这起漏洞由安全公司 Calif、OpenAI、Wiz 等多方借助 AI 工具发现，协调披露过程还被提前泄露和单方面打破，是“AI 加速找漏洞”的一个标志性事件。**

**本文面向普通人，讲清它到底是什么、对个人数据和资金安全有什么影响、个人该怎么防，同时给出对银行等金融机构的启示。**

## 一、php2shell 是什么

1. **两个相关漏洞**：CVE-2026-109618 是“内存溢出导致内存破坏”，CVE-2026-109619 是“陈旧状态导致释放后使用”，二者都位于 PHP 几乎每个请求都会经过的内存管理和错误处理环节。
2. **评级为严重**：官方评分是 CVSS v4.0 9.2；泄露到网络上的“10.0 分”是错误信息。
3. **补丁已发布**：受支持分支的修复版本为 8.5.12、8.4.27、8.3.36、8.2.35；官方还罕见地为 7.4、8.0、8.1 等已停止支持的版本提供了最小源码回移。
4. **影响运行时本身**：这不是 WordPress、Drupal 等某个应用的漏洞，而是 PHP 运行时的漏洞，只升级应用、不升级底层 PHP 并不够。
5. **波及所有网页部署**：PHP-FPM、Apache mod_php、php-cgi、FrankenPHP、LiteSpeed 等处理网页请求的方式都可能受影响，其中 Apache mod_php 风险最高。

## 二、用大白话讲原理

1. **内存溢出漏洞**：如果一个请求恰好在 PHP 内存达到上限的错误时刻中断，会留下“只初始化了一半”的内部数据，之后清理时被当成有效数据，从而破坏内存、执行恶意代码。
2. **构造方式**：官方说明，特制的 HTTP multipart 表单请求，比如异常多的表单头、嵌套或空的文件字段，可造成内存不成比例地耗尽。
3. **陈旧状态漏洞**：一个致命错误在错误时刻发生，可能让内部状态仍指向“上一个请求”已释放的内存，同一个工作进程处理下一个请求时就会误用这块内存。
4. **确认路径**：涉及会话上传进度处理，以及 PHP 8.5 的致命错误回溯状态；官方已在 Apache mod_php 和 PHP-FPM 上验证了远程代码执行。
5. **没有完整变通方案**：官方强调，配置层面的临时措施只能降低特定攻击路径的暴露，无法让未打补丁的系统变得安全，唯一完整的缓解就是更新。

## 三、为什么影响面这么大

1. **PHP 支撑大量网站**：大量网店、内容网站、政府服务、银行与媒体页面，以及 WordPress 等建站系统都运行在 PHP 之上。
2. **攻击无需登录**：未认证远程代码执行意味着攻击者只要能访问网站，就可能接管服务器，不需要任何账号密码。
3. **应用层防护失效**：漏洞可在请求启动、应用代码执行前触发，认证、授权、应用层规则都可能被绕过。
4. **内嵌 PHP 容易被忽略**：容器、虚拟设备、主机控制面板、第三方产品可能自带 PHP 运行时，版本号还可能因发行版回移补丁而具有迷惑性。
5. **暴露窗口被缩短**：补丁提前泄露、PoC 视频外传、有厂商提前发布含修复镜像，加速了攻击概念验证的传播。

## 四、对个人安全的影响

1. **个人数据可能被窃**：一旦网站服务器被接管，攻击者可窃取姓名、手机号、地址、订单、聊天记录等个人信息。
2. **支付信息有风险**：在小网站绑定银行卡、开通免密或保存支付信息的用户，可能面临支付信息被盗用、异常扣款的风险。
3. **网站可能被挂马**：被攻破的网站可能被植入钓鱼页面、恶意跳转或诈骗内容，让访问者在不知情中中招。
4. **账号可能被接管**：攻击者可借助服务器权限重置凭证、伪造登录或扩展到关联账户。
5. **个人站长风险更直接**：自己搭博客、开店、跑论坛的人，若运行在未修复的 PHP 上，服务器可能被直接控制。
6. **不必过度恐慌**：官方在发布时表示，尚未发现功能完整的在野利用，只要所用网站及时更新，风险可控。

## 五、个人该怎么办

1. **普通用户无需也无法直接打补丁**：你的安全取决于所使用的网站、App、主机商是否及时更新，个人重点是降低暴露、提高警觉。
2. **关注服务方公告**：留意常用网站、支付平台、电商是否发布安全修复或系统维护通知，必要时可主动询问客服。
3. **开启两步验证**：对邮箱、支付、网银、社交等重要账户开启两步验证，使用各自独立的强密码，避免一个泄露连累多个账户。
4. **谨慎绑定支付信息**：近期尽量不在陌生小网站保存银行卡或开通免密，优先使用有担保的第三方支付，开通交易提醒。
5. **警惕钓鱼与异常**：小心来历不明的邮件、短信、优惠券和网站重定向，核对域名，发现异常登录、扣款立即冻结并报失。
6. **个人站长立即升级运行时**：登录主机或面板，把 PHP 升级到 8.5.12、8.4.27、8.3.36 或 8.2.35，并重启所有 PHP 工作进程。
7. **共享主机联系服务商**：无法自行升级的，确认主机商是否已修复两个 CVE；不要只看“PHP 版本号”，要以厂商安全公告为准。
8. **暂时无法升级先隔离**：把非公开页面限制到可信网络或 VPN，关闭不必要的文件上传与 multipart 表单，尽快安排维护窗口。

## 六、AI 找漏洞的标志性意义

1. **并非“ChatGPT 单挑”**：官方致谢显示，主要由 Calif 的研究员 Ryan A、OpenAI Codex Security（Amy Burnett）、Wiz 等多方报告，借助了 Anthropic Claude Mythos、OpenAI Daybreak Red 等工具，最终判断和补丁都由人完成。
2. **根因早有端倪**：2024 年 PHP 首次外部审计（Quarkslab 实施，德国主权技术机构资助）时就发现了内存溢出问题的苗头，但当时没有找到具体利用路径。
3. **AI 让报告激增**：自 2026 年 7 月 1 日起，PHP 已发布 15 个 CVE，并处理了 100 多份无效、重复或不可复现的报告。
4. **攻防双方都更快**：AI 同时帮防御者和攻击者发现漏洞，防御窗口被压缩，这是所有机构都要面对的新常态。
5. **协调披露更脆弱**：这次泄露、误发视频和单方面打破 embargo，说明多方协同披露在 AI 时代更容易被打乱。

## 七、对银行的八点启示

1. **底层运行时风险高于应用层**：漏洞在应用代码执行前触发，说明银行再完善的应用层认证和 WAF 也挡不住运行时缺陷，运行时与组件治理必须前置。
2. **资产清点是第一要务**：网银、门户、营销活动页、合作方接口，以及容器、设备、第三方产品内嵌的 PHP 都要摸清，不能只看默认命令行版本。
3. **版本号会骗人**：发行版可能回移补丁而不改版本号，应以厂商安全公告、包变更记录和实际构建为准，核实两个 CVE 是否都已修复。
4. **补丁窗口要缩短**：AI 加速漏洞挖掘与 PoC 传播，银行需建立快速应急补丁机制，而不是按常规月度节奏。
5. **第三方与供应链是重点**：漏洞可通过主机商、设备、镜像、商用产品进入，第三方安全评估和合同披露义务必须强化。
6. **监测要结合行为特征**：关注异常 multipart 请求、工作进程崩溃、内存耗尽、异常子进程与外联，但这些是排查线索而非确定指标。
7. **开源底座需要投入**：PHP 这类关键基础设施长期依赖少量资金和人力，银行作为受益者应关注并支持开源安全维护。
8. **AI 安全研究要纳入防御**：银行应主动用 AI 工具做代码审计、根因归并与验证，缩短从发现到修复的时间。

## 八、银行的落地建议

1. **立即开展 PHP 资产清点**：覆盖所有 SAPI、容器、设备、面板和第三方产品，标记公网暴露、接受不可信请求的系统优先。
2. **按分支快速修复并验证**：升级到对应安全版本，重启全部工作进程，确认新请求由已修复的运行时处理。
3. **建立嵌入式运行时台账**：对无法直接升级的设备和产品，向厂商索取修复证明，必要时先隔离或下线。
4. **临时措施与补丁并行**：无法立即升级的，限制访问、约束请求体与上传、关闭会话上传进度等，但不得把临时措施当作最终修复。
5. **强化供应链与第三方管理**：在采购合同中约定安全更新时限、漏洞披露义务和配合审计责任。
6. **部署运行时监测与应急**：监控可疑请求、崩溃与内存事件，保留日志，按证据排查是否已被入侵。
7. **常态化 AI 辅助审计**：用 AI 工具做代码与组件扫描、报告归并和复现验证，同时由人做最终判断。
8. **支持关键开源基础设施**：评估对 PHP Foundation 等项目的赞助或参与，把开源安全纳入企业技术责任。

## 结语

php2shell 给普通人上了一课：我们每天使用的网站、支付和服务，其实都站在一层看不见的“运行时”地基上，当地基出现裂缝，个人的数据、账号和资金都可能受到牵连。对个人而言，最好的防护不是恐慌，而是认清自己无法直接修补，转而通过两步验证、独立密码、谨慎绑定支付、紧盯异常，并在自己建站时第一时间升级运行时。对银行而言，这起事件更像一次压力测试：它证明在 AI 时代，漏洞发现更快、攻击更底层、披露更脆弱，唯有把资产清点、运行时治理、供应链管理和快速应急连成一体，才能守住地基。**当 AI 让全世界的漏洞更快浮出水面，无论是个人还是银行，真正的安全都来自同一件事——把基础打牢，把补丁打快，把警觉放在平时。**
