**DeepSeek Harness（dsh）是 DeepSeek 官方开源的智能体运行框架，负责把模型和文件、终端、工具、插件连起来执行任务；“DeepSeek Bot”是社区开发者在它之上做的插件，把 dsh 变成一组有名字、有角色、有长期记忆的 Bot 团队（来源1、4）。**

**两者是“底座”和“上层应用”的关系，不是两个竞品：没有 dsh，DeepSeek Bot 跑不起来；不装 DeepSeek Bot，dsh 照样能用（来源4、5）。**

**“DeepSeek Bot”不是 DeepSeek 官方产品，而且同名项目至少有两个：Fei2411 维护的 DS Bot（npm 包 ds-bot，Apache-2.0）和 BotHarness 维护的 DeepSeekBot（npm 包 deepseekbot，MIT），二者互不相关（来源4、5、6）。**

**dsh 官方明确：它仍是开发者预览版，未经安全审计，不得视为安全或可用于生产环境；其官方模型服务条款还禁止用于“自动化信用资格判定”等高风险活动（来源2、3）。**

**对银行来说，结论是：dsh 可以在隔离环境里做研发和办公类试点；DeepSeek Bot 这类社区插件只适合个人或小团队探索，进入任何涉及客户数据或业务决策的场景前，都需要完成开源组件准入和安全评估（本文分析）。**

## 二、DeepSeek Harness：官方的智能体底座

### 2.1 它做什么

- **定位**：DeepSeek 开源的智能体运行框架，基于 Cordis 的“一切皆插件”架构（来源1）。
- **时间线**：2026 年 8 月 13 日以开发者预览版开源；9 月 29 日发布 v0.2 预览版，上线 macOS 与 Windows 桌面端（来源1、7）。
- **运行方式**：一条 `npx @deepseek-ai/dsh web` 命令即可在本机 3080 端口启动 Web 界面，也可以从源码构建（来源1）。
- **两种模型模式**：使用 DeepSeek 官方模型需登录账号并在开放平台预付费；也可以接入自己获取的模型 API，此时 dsh 只提供本地运行的交互界面和工具，**不在服务端存储或处理输入输出**（来源3）。

### 2.2 官方自己划的红线

SAFETY.md 和使用条款给出了非常直白的风险提示（来源2、3）：

1. 仍是实验性开发者预览版，**未经安全审计**，不得视为安全或可用于生产。
2. 它能执行模型生成的代码和命令、加载第三方插件、访问网络、进程、凭据和文件；模型出错、配置错误、恶意输入或不可信插件可能损坏主机、删除文件、泄露数据或凭据。
3. 沙箱、审批和权限控制能降低风险，但**不能保证隔离**，也保护不了已经授权给它的资源。
4. 第三方插件、MCP 服务、Skills、Hooks 由第三方提供，DeepSeek 不负责。
5. 官方模型服务禁止用于高经济风险活动，条款举例包括**自动化信用资格判定**以及就业、教育决策。

官方给出的建议包括：最小权限、优先在一次性虚拟机或容器中运行、备份可访问文件、重大操作必须人工确认、只安装可信来源且经过审查的插件（来源2、3）。

## 三、DeepSeek Bot：社区做的“Bot 团队”上层

### 3.1 DS Bot（ds-bot）

- **核心能力**：每个 Bot 有独立名称、职责、指令、形象和模型；有长期记忆；首次打开会自动创建主管 Bot“Chief”，它拥有很高权限，可管理其他 Bot 和群聊（来源4）。
- **群聊协作**：每个群有管理员，默认由管理员回复并调度其他 Bot，以减少 token 消耗；群聊有独立记忆，群外不可见（来源4）。
- **能力库**：MCP、Skills 等能力在设置中统一管理，Bot 新增本地 MCP 命令需用户批准（来源4）。
- **部署形态**：dsh 桌面端或 Web 端插件、自带 dsh 的独立桌面应用，以及面向 NAS 和常开服务器的 Docker 镜像；README 说明容器就是 Bot 的沙箱，挂载进去的内容 Bot 可完全访问（来源4）。
- **数据**：全部存放在本机 dsh 目录（默认 `~/.dsh`）下的 `bot/` 与 `sessions/`，**卸载插件不会删除这些数据**（来源4）。
- **成熟度**：README 标注为 v0.2 预览版，依赖 dsh 0.2.1-rc.2；仓库 2026 年 10 月 7 日创建，截至本文写作约 3200 星（来源4）。

### 3.2 DeepSeekBot（deepseekbot）

- 由 BotHarness 维护，npm 当前版本 1.4.1，MIT 许可（来源6）。
- 主打用 Git 工作树管理 Bot 记忆（可看提交和差异）、独立的任务委派会话，以及飞书、Slack、Discord、QQ、微信等 IM 身份（来源5、6）。
- 其团队文章说明：1.2.0 版本的 npm 发布包不含电脑/浏览器 GUI 自动化组件（来源5）。

### 3.3 两层的差别一览

| 维度 | DeepSeek Harness | DeepSeek Bot（以 DS Bot 为例） |
|---|---|---|
| 层级 | 运行框架（底座） | 框架上的插件（应用层） |
| 责任主体 | DeepSeek 官方 | 个人或社区团队 |
| 交互形态 | 单会话为主，执行任务、写代码、处理文件 | 多个长期存在的 Bot，群聊协作、主管调度 |
| 记忆 | 会话日志与回放 | 每个 Bot 的长期记忆、团队记忆、群记忆 |
| 权限模型 | 审批、沙箱、权限控制 | 在 dsh 之上再加主管 Bot、群管理员等角色权限 |
| 成本特征 | 按任务调用模型 | 多 Bot、群聊会放大模型调用量 |
| 成熟度 | 开发者预览，未经安全审计 | 早期预览，迭代极快 |

**本文分析**：把 Bot 插件叠在 dsh 上，并不会降低风险，而是在原有风险之上再加三类新风险——高权限主管 Bot、跨会话持久化的记忆，以及 Bot 之间相互转派任务带来的责任链变长。

## 四、银行能用在哪里（本文分析）

### 4.1 适合 dsh 的场景

| 场景 | 说明 | 前提 |
|---|---|---|
| 研发辅助 | 代码阅读、单元测试生成、遗留系统文档整理 | 隔离开发环境，脱敏代码或非核心系统 |
| 数据分析草稿 | 对脱敏数据做探索性分析、生成图表和报告初稿 | 只读数据副本，结果人工复核 |
| 制度与材料整理 | 汇总公开监管文件、起草内部培训材料 | 只用公开或内部非敏感材料 |
| 智能体能力研究 | 作为可替换插件的实验平台，研究审批、沙箱、轨迹审计 | 由金融科技或创新部门在实验室环境开展 |

### 4.2 适合 DeepSeek Bot 的场景

| 场景 | 说明 | 前提 |
|---|---|---|
| 个人研究助理团队 | 一个 Bot 收集公开资讯、一个比对、一个起草周报 | 仅限公开信息，不连生产系统 |
| 小组协作试验 | 研究“主管 + 专业 Bot”的分工模式能否降低成本、提升质量 | 测试数据，记录每个 Bot 的输出与依据 |
| 多智能体治理研究 | 观察记忆漂移、任务转派、权限扩散等问题 | 作为风险研究对象，而非生产工具 |

### 4.3 目前都不适合的场景

- **信贷审批、授信额度、风险评级等决策**：dsh 官方模型条款明确禁止自动化信用资格判定，且两者都未达生产就绪（来源3）。
- **直接接入核心系统、支付、客户账户**：官方声明已提示可能删除文件、泄露凭据（来源2）。
- **处理客户个人信息**：社区插件的记忆数据在本地长期保存，卸载也不删除（来源4），数据生命周期难以满足个人信息保护要求。
- **对外客服或营销**：输出须标注 AI 生成且需人工核实（来源3），社区插件的 IM 接入更会把风险直接暴露给客户。

## 五、怎么选、怎么部署（本文分析）

**本节全部为本文分析。**

### 5.1 三问决策

1. **是否需要多个长期角色协作？** 不需要就只用 dsh；需要再评估 Bot 插件。大多数单人任务，一个会话加清晰指令就够了，多 Bot 只会增加调用量和审查负担。
2. **数据是什么等级？** 公开数据可试；内部一般数据需隔离环境；客户信息和敏感经营数据当前阶段不进入。
3. **由谁承担责任？** 官方框架有明确的责任主体和使用条款；社区插件的维护依赖个人或小团队，需要评估其更新频率、漏洞响应和替代方案。

### 5.2 部署形态选择

| 形态 | 适用 | 银行注意事项 |
|---|---|---|
| 员工个人电脑桌面端 | 个人探索 | 不建议在办公终端直接安装；易接触真实文件和凭据 |
| 隔离虚拟机或容器 | 研发与研究试点（推荐） | 只挂载必要目录，网络出口白名单，用完即弃 |
| 行内私有服务器 + 自有模型 | 部门级试点 | 用“自定义模型”模式接行内部署的模型，输入输出不经 DeepSeek 服务端（来源3） |
| 官方模型 API | 公开数据实验 | 数据出境与跨机构传输需走合规评估 |
| 社区 Docker 镜像（如 DS Bot） | 常驻 Bot 试验 | 镜像来源需审查，挂载目录即 Bot 的全部可访问范围（来源4） |

### 5.3 上线前的七项底线

1. **开源组件准入**：dsh、插件及其依赖逐一登记许可证（MIT、Apache-2.0）、维护方与版本，锁定版本号，禁止自动升级。
2. **插件白名单**：只允许经安全审查的插件、MCP 服务和 Skills；社区插件市场的插件默认不放行。
3. **最小权限**：不给真实生产凭据；文件访问限于专用工作目录。
4. **高权限角色控制**：如使用 DS Bot，主管 Bot 的权限要单独评估，避免“一个 Bot 能改所有 Bot”。
5. **记忆治理**：Bot 记忆是新的数据资产，要定义谁能写、多久清理、如何审计；卸载前手动清除本地数据。
6. **人工确认**：任何写操作、对外发送、代码合并都必须人工批准，并保留执行轨迹。
7. **成本监控**：多 Bot 群聊会放大调用量，设置额度上限和按 Bot 的用量报表。

## 六、结语

**本文分析**：DeepSeek Harness 和 DeepSeek Bot 代表了智能体落地的两层：前者解决“模型如何安全地动手”，后者尝试“多个智能体如何长期协作”。对银行而言，真正要选的不是“用哪一个”，而是“先在哪一层建立治理能力”。建议先在隔离环境中用 dsh 建立审批、沙箱、轨迹审计和插件准入机制；等底座治理成熟、官方版本稳定，再把多 Bot 协作作为下一阶段的研究课题。

## 常见问题

Q: DeepSeek Bot 是 DeepSeek 官方出的吗？

A: 不是。目前名为 DeepSeek Bot 的项目是社区开发者基于 DeepSeek Harness 做的插件，主要有 Fei2411 的 DS Bot（ds-bot）和 BotHarness 的 DeepSeekBot（deepseekbot）两个，均声明非官方（来源4、5）。

Q: DeepSeek Harness 和 DeepSeek Bot 是什么关系？

A: DeepSeek Harness 是底层智能体运行框架；DeepSeek Bot 是安装在它上面的插件，把它变成多个有长期记忆、可群聊协作的 Bot（来源1、4）。

Q: 银行能把 DeepSeek Harness 用于生产吗？

A: 目前不建议。官方安全声明和使用条款都写明它是未经安全审计的开发者预览版，不得视为可用于生产环境（来源2、3）。

Q: 银行试点应该怎么部署？

A: 建议在隔离虚拟机或容器中运行 dsh，通过“自定义模型”模式接入行内部署的模型，只使用公开或脱敏数据，插件实行白名单，所有写操作人工确认（本文分析）。
