# 让模型分清敌我

**IBM 在 11 月 12 日发布两个实验性 Granite 模型（3B 和 8B 预览版），专门训练来抵抗提示注入，核心是把可信指令和不可信数据分离开。**

**这套方法基于 LLMON，一种类似 XML 的标记语言，读作 Lemon，用特殊保留 token 给文本里的指令和数据分别打上标签。**

**关键在于特权规则不是外部过滤器，而是模型自己内化：只有执行块明确授权的指令才会被执行，数据里藏的命令被当成待处理信息忽略。**

**IBM 称这两个模型比测试过的最佳前沿模型多避免 47% 的攻击，同时在标准任务上与普通 Granite 4.1 持平，安全不牺牲能力。**

**对银行而言，这是 Agent 安全纵深防御里重要的模型层一环，但它仍是实验预览，需要应用侧配合改造并自行红队验证，不能当作免疫银弹。**

## 一、提示注入为什么是 Agent 头号威胁

1. **问题根源**：大模型把所有输入都当成同一种 token 流，天然不区分系统给的指令和外部世界的数据，二者在同一上下文里竞争对模型的影响力。
2. **直接注入**：用户直接对模型说忽略之前的指令、改按新规则办，这类相对容易识别。
3. **间接注入更危险**：恶意指令藏在模型要处理的外部数据里，比如网页、邮件、PDF、文档、图片识别结果或工具返回值，Agent 为了干活又不能不读这些内容。
4. **Agent 放大危害**：Agent 手里有发邮件、查数据库、调核心系统甚至执行代码的工具，一旦被注入，就可能把数据里的恶意指令当成任务，造成数据泄露、越权操作和资金损失。
5. **银行的现实暴露面**：银行 Agent 每天要处理大量外部来件和文档，一封带注入的邮件、一份带注入的对账单，都可能成为攻击入口。

## 二、LLMON 是什么：给文本染色

1. **论文来源**：LLMON 全称 LLM Object Notation，相关论文在 2026 年 3 月首次提交，出发点是纯字符串接口丢失了 prompt 内部的结构和语义。
2. **核心思想**：用标签给文本片段染色，标明哪段是指令、哪段是数据，类似编程语言里的类型系统，让结构信息能被训练和推理环节利用。
3. **标记方式**：用特定序列标记一类片段的开始和结束，整体语法类似 XML，人和模型都能读懂。
4. **防伪造设计**：分隔符由特殊保留 token 和两字符的块标识符构成，每个标识符恰好占两个 token，外部数据无法自然生成这些特殊 token，从而难以伪造标签冒充指令。
5. **类比**：这就像给文件加上系统级的可信标记，外部内容即使写满了命令字样，也拿不到指令的身份。

## 三、关键：让模型自己内化特权规则

1. **传统做法的局限**：输入过滤、关键词黑名单容易被变体和编码绕过，外部护栏模型增加延迟和成本，且属于事后检查，没有解决模型本体混淆指令和数据的问题。
2. **执行机制**：LLMON 配套一个执行块，模型在训练中学会只认执行块明确授权的指令，数据块里的任何命令都被当作需要处理的信息而非要执行的动作。
3. **特权内化**：这条规则不是外挂的过滤器，而是模型权重内化的判断，模型从根上知道自己该听谁的。
4. **多轮场景**：机制考虑了多轮对话，攻击者即使在后续轮次、通过不同材料反复尝试，也难以让模型越过可信边界。
5. **思路转变**：从在模型外面加关卡，转向让模型本身具备敌我识别能力，这是更靠近根因的防御路线。

## 四、Granite 4.1 LLMON 的实测数据

1. **两个规格**：基于 Granite 4.1 的 dense decoder-only 架构，提供 3B 和 8B 两个预览版本，都属于实验性质。
2. **安全效果**：IBM 报告称，在提示注入相关测试中，这两个模型比其测试过的最佳前沿模型多避免 47% 的攻击。
3. **能力不打折**：官方称在标准任务类别上，LLMON 版本与普通 Granite 4.1 Instruct 表现持平，安全增益没有以牺牲通用能力为代价。
4. **小模型的价值**：3B、8B 体量便于私有化部署、成本低、可控性强，适合作为专用安全节点，而不是所有环节都依赖大模型。
5. **配套生态**：IBM 同时有 Granite Guardian 护栏模型，负责检测幻觉、有害内容和越狱，形成模型本体加外部护栏的组合。

## 五、银行视角：纵深防御怎么搭

1. **模型层**：在处理外部不可信内容的 Agent 上，优先选用能区分指令和数据、具备模型级抗注入能力的模型，并私有化部署敏感场景。
2. **数据层**：所有外部来件明确标记为不可信，按最小权限原则提供给模型，默认外部数据只有被处理的资格、没有下命令的资格。
3. **工具层**：涉及资金、授信、客户信息的高危动作必须保留人工审批和权限隔离，模型再可信也不直接放行。
4. **监控层**：用护栏模型和审计日志持续监测异常指令、越权调用和异常输出，像监测交易一样监测 Agent 行为。
5. **可信边界**：把系统指令、企业知识、外部数据放进不同信任等级，和银行既有的安全域、权限分级思想对齐。

## 六、四个冷静判断

1. **仍是实验预览**：两个模型明确标注为实验性，不是生产成熟产品，直接上核心业务还为时过早。
2. **数据要复核**：47% 是 IBM 在自有测试和特定基准上的一方口径，基准选择、攻击样本和对比对象都影响结果，不代表对真实攻击免疫。
3. **需要应用侧改造**：LLMON 要求输入按标记格式封装，模型和应用要一起改造，不是换个模型就自动生效。
4. **攻防是动态的**：没有一劳永逸的银弹，模型级防御必须和数据、工具、监控层治理结合，并持续用红队测试更新防线。

## 七、和本站其他文章的呼应

1. **和强模型要审查用呼应**：准入审查解决能不能用，LLMON 解决用起来之后怎么不被外部内容带偏，是同一控制体系的两段。
2. **和买 Agent 还是造 Agent 呼应**：无论采购还是自研，抗注入能力和可审计性都应是选型硬指标，而不是事后补救。
3. **和看懂 AI 就安全吗呼应**：可解释性帮助看清模型，LLMON 帮助约束模型，一个解决看懂、一个解决管住，缺一不可。

## 结语

提示注入的本质，是模型分不清哪句话是主人的命令、哪句话是外面的噪声。IBM 用 LLMON 给出的答案，是把这种身份判断从外挂规则变成模型内化的本能，再用特殊 token 防止外部数据伪造身份。这代表了 Agent 安全一个清晰的方向：与其在混乱的输入外面层层设防，不如让模型从一开始就知道该听谁的。但对银行来说，再强的模型级防御也只是纵深体系中的一层，数据标记、权限隔离、人工审批和持续监控一个都不能少，而且所有厂商数字都要在自己的红队测试里重新验证。
