# MCP学会协作

**11月24日，Anthropic升级模型上下文协议：技能下发开启公测，后台任务与交互征询正式可用，文件上传即将推出。**

**这次升级的本质，是MCP从一个连接工具的“插座”，进化为支持完整智能体工作流的协作层。**

**技能、任务、征询三个新能力，恰好对应银行在专业合规、长流程授权、人工确认上的三个治理痛点。**

**Elicitation第一次把“执行中途停下来向人请示”做成标准协议原语，是银行双人复核与高风险授权的技术支点。**

**随工具动态下发的技能本质是远程可执行内容，构成新的供应链攻击面，必须像管理代码一样管理技能。**

## 一、MCP两岁：从插座到协作层

1. **两年前的起点**：2024年11月，Anthropic推出模型上下文协议，目标是给AI智能体提供一个连接外部数据与系统的统一标准，解决每个应用都要单独对接的碎片化问题。
2. **中立治理**：MCP是开放标准，2025年底捐赠给Linux基金会旗下的智能体AI基金会托管，由生态共同维护，不再属于单一厂商。
3. **生态规模**：据Anthropic披露，MCP的SDK月下载量已超过7亿次，面向Claude的连接器超过1万个，这两个数字是厂商口径，反映其已成为事实标准。
4. **过去只解决“怎么连”**：在本次升级前，MCP的核心是工具调用，服务器通过工具名称和描述告诉模型“我能做什么”，但无法告诉模型“具体业务该怎么做”。
5. **现在解决“怎么协作”**：升级后，Claude与服务器的关系更像与另一个智能体协作——向它学习、给它委派任务、在过程中交换信息和文件，这是从连接层到协作层的质变。

## 二、Skills over MCP：把操作手册随工具下发

1. **公测状态**：Skills over MCP目前处于公开测试阶段，在Claude和Claude Code中，Pro、Max、Ultra套餐默认开启，Team套餐需管理员启用，企业版即将推出。
2. **解决什么问题**：工具名称和描述只能说明能力边界，无法承载多步骤业务的处理方法，技能则把专业知识和操作流程一起提供给模型。
3. **按需加载**：模型只在任务需要时才加载对应技能，平时仅加载约100个token的元数据，从而把上下文消耗控制在较低水平。
4. **随服务器更新**：技能与工具一同发布、随服务器同步更新，用户无需单独安装，开发者可以把工具和使用指南一起迭代。
5. **可定制**：技能可以包含最佳实践、分步工作流，甚至针对特定用户账户或组织定制的操作手册。
6. **落地案例**：Shopify用它让Claude端到端设计和更新网店，HubSpot用于客户引导配置，Atlassian帮助调用组织上下文做分析，Carta即将支持从上传文档起草和发行股权。

## 三、Tasks：让长任务在后台跑起来

1. **正式可用**：Tasks已在Pro、Max、Ultra套餐正式可用，并陆续向Team和企业版推出。
2. **过去的阻塞**：此前模型必须等待一次工具调用完成才能继续，遇到耗时操作就会被卡住，无法并行处理。
3. **现在的异步**：服务器可以返回一个任务句柄，在后台运行耗时操作甚至完整的智能体循环，模型同时继续做其他工作，就绪后再取回结果。
4. **落地案例**：ZoomInfo用Tasks运行更深入的账户与联系人研究，这类工作过去需要多个提示反复推进。
5. **治理含义**：后台任务意味着工作脱离了实时对话、运行时间被拉长，银行需要对“放出去还在跑的任务”建立授权范围、超时、资源限额和可中断机制。

## 四、Elicitation：执行中途停下来请示

1. **正式可用**：Elicitation与Tasks同期正式可用，覆盖同样的套餐范围。
2. **核心机制**：服务器可以在工具调用中途暂停，通过表单或链接向用户征求输入或授权，然后从断点继续执行。
3. **典型场景**：花钱、删数据这类动作需要用户签字确认，Elicitation把这个确认环节嵌入了执行流程。
4. **Supabase**：在创建付费项目前确认成本，在执行破坏性SQL前再次征求确认。
5. **Railway与GitHub**：Railway在移除服务等潜在破坏性变更前询问，GitHub则要求用户手动输入仓库名称，才允许智能体删除该仓库。
6. **关键意义**：人工否决不再是流程外的口号，而是被做成了协议内置的标准能力，模型可以被强制在关键动作前停下来等人。

## 五、File Uploads：文件带外传输

1. **即将推出**：文件上传功能正在陆续发布，面向Pro、Max、Ultra及符合条件的Team和企业版。
2. **机制**：模型可以把PDF、电子表格、图片等文件直接传给MCP服务器，而不只是传递文本。
3. **带外通道**：文件通过扩展带外发送，不经过上下文窗口，避免大量文件内容挤占和泄露在对话上下文中。
4. **仍属实验**：开发者文档把它标注为实验性扩展上的测试能力，正式日期尚未给出。
5. **治理含义**：文件带外流动要求银行明确哪些文件可外发、流向何处、是否留存，防止敏感文件在不可见链路中扩散。

## 六、三个能力对应银行三个治理痛点

1. **技能对应“模型不懂银行规矩”**：通用模型不天然掌握信贷、合规、内控的专业流程，技能把这些规矩工程化、可复用，让模型按银行的剧本办事。
2. **任务对应“长流程效率与可控”**：风控核查、客户尽调、批量分析往往耗时长，Tasks让它们后台并行，但必须配套任务级授权和可观测。
3. **征询对应“高风险动作必须有人确认”**：资金划转、数据删除、配置变更不能由模型独自完成，Elicitation提供了强制人工确认的技术实现。
4. **三者构成闭环**：技能提供“怎么做”，任务负责“后台做”，征询保证“关键处等人拍板”，合起来是一个可治理的智能体工作流。
5. **与既有体系衔接**：这套能力不是另起炉灶，而是把银行熟悉的制度规范、授权审批、双人复核映射到智能体协议层。

## 七、Elicitation为什么对银行特别重要

1. **呼应maker-checker**：银行的核心控制之一是经办与复核分离，Elicitation让系统在高风险动作前强制暂停，天然适配这一机制。
2. **限额与授权可落地**：超过限额、触及特殊权限的操作，可以通过征询环节触发更高级别审批，而不是在模型层面静默放行。
3. **可审计**：确认动作通过表单和链接发生，确认了什么、何时确认、由谁确认，都可以结构化记录进审计日志。
4. **冷静的边界**：Elicitation是协议能力，不等于风险自动可控，是否真确认、确认内容是否被正确理解、能否被其他链路绕过，仍取决于实现和配置。
5. **防止“橡皮图章”**：银行要警惕用户把确认弹窗变成机械点击，应让确认信息足够清晰、与具体动作强绑定，避免人工确认流于形式。

## 八、新攻击面：技能即远程可执行内容

1. **技能本质是指令**：SKILL.md文件承载的是给模型的操作指令，随服务器动态下发，本质上是一种远程可执行内容，而非静态文档。
2. **指令覆盖风险**：安全研究显示，恶意技能可在正文中嵌入“忽略此前所有指令”等覆盖语句，加载后直接进入模型上下文，与系统提示并列。
3. **提示分隔符注入**：攻击者可伪造上下文分隔标记，诱导模型把恶意内容当作系统指令，这是技能摄取管道特有的新攻击面。
4. **自动加载被诱导**：在自动模式下，分类器可能在未读取技能全文时就决定加载，存在被触发词和描述诱导加载恶意技能的风险。
5. **Rug Pull问题**：服务器可先提供良性技能获取信任，再通过更新改变其行为，技能随服务器更新的便利也放大了这种“变脸”风险。
6. **权威佐证**：OWASP、MCP官方文档和arXiv研究都把供应链投毒、工具投毒、提示注入列为MCP生态的核心风险，并非理论假设。

## 九、信任边界外移：从信任工具到信任整个服务器

1. **过去的信任对象**：采用MCP时，银行主要评估一个工具是否可信、权限范围多大。
2. **现在的信任对象**：升级后，银行实际信任的是工具、它动态下发的技能、它后台运行的任务，以及它处理的文件，信任边界整体外移。
3. **混淆代理问题**：MCP官方指出，若服务器接受并向下方转发未正确校验受众的令牌，可能形成混淆代理，让下游接口误信请求来源。
4. **过度权限风险**：OWASP提醒，服务器常请求宽泛的OAuth作用域，多个能力叠加后形成聚合风险，一个连接可能拿到远超必要的权限。
5. **最小权限仍是基座**：无论协议如何演进，最小权限、作用域隔离、令牌有时限可撤销，仍是控制信任边界的根本手段。

## 十、开放标准的双刃剑

1. **标准化的收益**：跨客户端兼容、不被单一厂商锁定，银行不必为每种AI产品单独集成，这与本站此前分析的受控开放逻辑一致。
2. **标准化的代价**：当连接和技能都遵循同一规范，攻击模式、投毒手法也可被规模化复用，一处漏洞可能影响大量兼容客户端。
3. **集中度风险**：7亿月下载、1万连接器背后，是对少数标准、云和模型供应商的共同依赖，可能形成跨机构的系统性风险。
4. **企业治理在补齐**：Anthropic同期推出企业托管授权、零数据保留等能力，说明标准方也在为受监管行业补齐治理工具，但部分仍处于测试阶段。
5. **理性态度**：开放标准解决了“怎么连、怎么协作”，但“信任什么、如何治理”始终是银行自己的责任，不会因为采用标准而自动完成。

## 十一、银行落地治理清单

1. **技能准入审查**：把SKILL.md当作代码和内容资产，建立提交、审核、签名、发布流程，外部技能默认隔离、最小权限。
2. **版本锁定与变更管理**：对生产环境使用的技能锁定版本，服务器更新技能须重新审核，建立Rug Pull监测和变更告警。
3. **任务级授权**：为后台任务明确作用域、超时、资源限额，维护后台任务清单，支持实时查看、中断和撤销。
4. **强制人工确认**：用Elicitation把资金、删数据、配置变更等动作强制接入确认，明确哪些动作必须确认、对应何种审批级别。
5. **确认信息强绑定**：让确认表单清晰展示具体动作、金额和影响，防止通用确认和橡皮图章，确认记录纳入审计。
6. **全链路监测**：对技能加载、任务委派、征询确认、文件外发建立日志和异常检测，纳入统一安全运营。
7. **文件外发管控**：明确可外发文件类型、目的地和留存策略，敏感文件优先脱敏或在受控环境处理。
8. **区分内外部技能**：内部受控技能可逐步放开，第三方目录技能需经安全扫描，警惕名称仿冒和拼写陷阱。
9. **评估集中度**：梳理对少数标准、云、模型供应商的依赖，纳入第三方风险与运营韧性管理。
10. **灰度推进**：先在沙箱和小范围验证，待企业版治理能力成熟后再扩大，不盲目追新。

## 十二、四个冷静判断

1. **这是基础设施演进，不是模型突变**：本次变化在协议和协作方式层面，提升的是工作流的可组合性，而非某个模型突然无所不能。
2. **部分能力仍在测试**：技能下发和文件上传尚未完全正式，企业版能力也未全部就绪，生产环境应保留谨慎。
3. **数据多为厂商口径**：下载量、连接器数等来自Anthropic一方披露，应作为厂商自述看待，而非独立审计结论。
4. **安全不会自动获得**：确认弹窗、开放标准都只是工具，真正的风险控制仍取决于银行的实现、配置和运营纪律。

## 结语

这次升级最值得银行关注的，不是MCP又增加了几个功能，而是智能体的协作方式正在被标准化地重构：技能让专业流程可复用，任务让长流程可异步，征询让关键动作可确认。三者合在一起，第一次把“按规矩办事、后台高效执行、关键处有人拍板”这套银行最熟悉的控制逻辑，完整地映射到了智能体协议层。但同一枚硬币的另一面，是随服务器动态下发的技能把供应链攻击面进一步打开，信任边界从工具扩展到整个服务器。务实的做法既不是因为出现了人工确认原语就认为风险已解，也不是因为新攻击面就拒绝采用，而是把技能当代码治理、把任务当授权对象、把确认当控制点来建设，在开放标准之上重建属于自己的信任边界。这才是智能体协作时代银行真正需要掌握的基本功。
